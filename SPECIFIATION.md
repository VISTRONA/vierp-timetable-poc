# VIERP Timetable Automation POC
## Full System Design & Technical Specification


> **Project:** VIERP Timetable Automation Proof of Concept  
> **Purpose:** Automatically populate timetable data from an externally generated Excel timetable instead of manually entering every class, teacher, room, subject and class type into VIERP.  
> **Known Target Stack:** Vue.js + Apache Grails/Groovy + MySQL  
> **POC Stack:** Vue.js + Apache Grails/Groovy + MySQL + Apache POI  
> **Primary Flow:** Excel → Upload → Parse → Validate → MySQL → Division JSON → REST API → Vue Timetable


---


# 1. Executive Summary


The current timetable workflow requires timetable information generated by a separate timetable-generation application to be manually entered into the VIERP ERP system.


The proposed Proof of Concept removes this repetitive manual process.


A user will upload the timetable Excel file once. The system will then:


1. Receive the Excel file through the Vue frontend.
2. Send it to the Apache Grails backend.
3. Store the original Excel file on the server.
4. Read the workbook using Apache POI.
5. Validate the Excel structure and individual rows.
6. Normalize the timetable information into a canonical data model.
7. Store the timetable records in MySQL.
8. Group/index timetable records by division.
9. Generate division-specific JSON.
10. Expose REST APIs.
11. Allow the Vue frontend to request a division.
12. Render the timetable quickly using the returned JSON/API data.


The POC is deliberately modular because the actual VIERP/EduPlus source code is not yet available.


Once the EduPlus team provides the real source code and database structure, the POC components can be adapted into the production system.

# 2. Problem Statement


The current process has several problems:


- Timetable data is generated by a separate timetable-generation application.
- Staff must manually enter that timetable into VIERP.
- Multiple dropdowns/fields must be populated for every class.
- Teacher, classroom, subject and class type information must be entered repeatedly.
- Manual entry consumes significant administrative time.
- Manual entry can introduce mistakes.
- Labs and subgroup classes require additional handling.
- Timetable entries can span multiple periods.
- The existing timetable-generation software already contains the information, so re-entering it is redundant.


The proposed system creates an automated bridge:


```text
External Timetable Software
          ↓
       Excel
          ↓
   VIERP Timetable POC
          ↓
  Automatically populated

6. Why Grails Instead of FastAPI?

The POC should use:

Vue.js
   ↓
Grails
   ↓
MySQL

rather than:

Vue.js
   ↓
FastAPI
   ↓
Grails
   ↓
MySQL

The reason is simple:

The actual VIERP backend is already known to use Apache Grails.

Adding FastAPI would introduce:

Another backend.
Another server.
Another deployment requirement.
Another API layer.
Another debugging layer.
Another integration point.

Grails can already process .xlsx files using Apache POI.

Therefore:

Do not introduce FastAPI into the POC unless a genuine Python-specific requirement appears later.

18. MySQL Design

For the POC, a simple timetable table is sufficient.

CREATE TABLE timetable_entries (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,


    division VARCHAR(100) NOT NULL,


    subject VARCHAR(100) NOT NULL,


    student_group VARCHAR(50),


    teacher VARCHAR(200),


    room VARCHAR(50),


    day VARCHAR(20) NOT NULL,


    start_time TIME NOT NULL,


    end_time TIME NOT NULL,


    periods INT DEFAULT 1,


    class_type VARCHAR(20),


    source_row INT,


    import_batch_id BIGINT,


    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,


    INDEX idx_division_day_time
        (division, day, start_time)
);

24. Why Division-Specific JSON?

Suppose the database contains thousands of timetable records.

The user selects:

ETC A

There is no reason to send the entire institution timetable to the browser.

Instead:

GET /api/timetable/ETC-A

returns only:

ETC A

This makes division switching fast and reduces frontend processing.

47. Performance Strategy

The key performance principle is:

Never make one API/database request per timetable cell.

Correct:

Select Division
      ↓
One API Request
      ↓
Receive all entries
      ↓
Store in Vue state
      ↓
Map entries locally
      ↓
Render cells

Incorrect:

Cell 1 → API
Cell 2 → API
Cell 3 → API
Cell 4 → API
...

Additional strategies:

Division-specific JSON.
MySQL index on division/day/start time.
Vue state caching.
One API request per selected division.
Data-driven cell rendering.
Avoid unnecessary database calls during rendering.

56. Core Architecture Principle

The entire system should follow one central rule:

Excel is an input format, not a frontend concern.

The canonical architecture is:

Excel
  ↓
Excel Parser
  ↓
TimetableEntry
  ↓
MySQL
  ↓
Division JSON
  ↓
REST API
  ↓
Vue
  ↓
Timetable

The Vue frontend should only care about the canonical timetable data.

The Grails backend should own:

Import.
Validation.
Storage.
Transformation.
API.

The Vue frontend should own:

User interface.
Division selection.
Grid calculation.
Cell rendering.

This separation is what will make the POC easy to integrate into the actual VIERP/EduPlus system later.

57. One-Line Project Definition

A modular Vue + Grails + MySQL timetable automation system that accepts an externally generated Excel timetable, automatically imports and indexes its records by division, exposes fast division-level JSON/API data, and renders each class timetable with subject, teacher, room, class type, group and multi-period information.
